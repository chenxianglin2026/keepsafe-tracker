# KeepSafe 开发团队管理制度

> 版本：v1.0
> 生效日期：2026-05-15
> 制定人：OpenClaw

---

## 一、团队组织架构

```
                    ┌──────────────┐
                    │   陈总       │
                    │ (产品决策人)  │
                    └──────┬───────┘
                           │
                    ┌──────┴───────┐
                    │  OpenClaw    │
                    │ (项目经理)    │
                    │ 架构·管理·审核 │
                    └──────┬───────┘
                           │
          ┌────────────────┼────────────────┐
          │                │                │
    ┌─────┴─────┐   ┌─────┴─────┐   ┌──────┴──────┐
    │ 子AgentA  │   │ 子AgentB  │   │  子AgentC   │
    │ (硬件/固件) │   │ (小程序)   │   │  (后端)     │
    └───────────┘   └───────────┘   └─────────────┘
```

### 角色定义

| 角色 | 人 | 职责 |
|------|-----|------|
| **产品决策人** | 陈总 | 定方向、做决策、验收结果 |
| **项目经理** | OpenClaw(我) | 架构设计、任务拆解、代码审查、团队管理、质量管理 |
| **子Agent A — 硬件固件** | 待招募 | 原理图、PCB、固件开发 |
| **子Agent B — 小程序** | 待招募 | 微信小程序开发 |
| **子Agent C — 后端** | 待招募 | 服务器端、API、数据库 |

## 二、开发流程规范

### 2.1 每个任务的标准流程

```
Step 1: 📋 编写开发方案
        ↓
Step 2: ✅ 方案审批（我来审）
        ↓
Step 3: 🧑‍💻 分派给子Agent开发
        ↓
Step 4: 🔍 代码审查（我来审）
        ↓
Step 5: 🧪 专人验证测试
        ↓
Step 6: 📦 合并入库
```

### 2.2 开发方案模板

每个任务必须包含以下内容才能开始编码：

```markdown
# 开发方案：[任务名称]

## 1. 需求描述
- 做什么？
- 为什么做？
- 验收标准是什么？

## 2. 技术方案
- 使用什么技术/框架？
- 架构图/流程图
- 关键接口定义

## 3. 工作量评估
- 预估工时
- 依赖的前置任务

## 4. 风险点
- 可能遇到的问题
- 备选方案

## 5. 测试方案
- 怎么验证是对的？
- 边界条件？
```

## 三、代码审查规范

### 3.1 审查标准

| 审查项 | 标准 |
|--------|------|
| 功能正确 | 符合开发方案定义的验收标准 |
| 代码质量 | 清晰、可读、有注释 |
| 安全性 | 无硬编码密钥、无SQL注入、无XSS |
| 性能 | 无明显性能问题 |
| 规范一致 | 符合项目代码规范 |

### 3.2 审查流程

```
子Agent提交代码
    ↓
我进行 Code Review
    ↓
  ┌─── 通过？───┐
  │            │
  是            否
  │            │
  ↓            ↓
合并入库      打回修改
             + 附审查意见
```

### 3.3 验证人制度

每个子Agent的产出，由**另一个子Agent**或**我**来验证，不能自己写自己验。

```
A写代码 → B审查验证
B写代码 → C审查验证
C写代码 → A审查验证
```

## 四、资料库管理制度

### 4.1 文件夹结构

```
~/projects/keepsafe/
├── docs/              ← 产品文档
│   ├── prd/           PRD需求文档
│   ├── specs/         技术规格书
│   └── scheme/        开发方案（每个任务一份）
│
├── src/               ← 源代码
│   ├── firmware/      固件代码
│   ├── miniapp/       小程序代码
│   └── backend/       后端代码
│
├── meetings/          ← 会议纪要
│   └── YYYY-MM-DD-主题.md
│
├── releases/          ← 发布版本
│   └── v0.1.0/        MVP版本
│
├── team/              ← 团队管理
│   ├── members.md     团队成员信息
│   ├── rules.md       团队制度
│   └── progress.md    进度跟踪
│
├── specs/             ← 技术规格书
│   ├── hardware-spec.md
│   ├── api-spec.md
│   └── protocol-spec.md
│
└── shared-memory/     ← 共享记忆库
    ├── decisions.md   决策记录（为什么选这个方案）
    ├── lessons.md     踩坑记录
    ├── glossary.md    术语表
    └── references.md  参考资料
```

### 4.2 文件命名规范

```
类型-日期-简要描述.md

示例：
scheme-20260515-固件GPS定位方案.md
meeting-20260515-phase0启动会.md
release-v0.1.0.md
```

## 五、共享记忆库制度

### 5.1 必须记录的内容

每次遇到以下情况，必须更新共享记忆库：

| 事件 | 记录到 | 内容 |
|------|--------|------|
| 做了一个技术决策 | decisions.md | 选了A方案没选B方案，原因 |
| 踩了一个坑 | lessons.md | 出了什么问题，怎么解决的 |
| 新学到一个经验 | lessons.md | 以后要注意什么 |
| 新增一个专业术语 | glossary.md | 这个词是什么意思 |
| 发现一个好的资料 | references.md | 链接+一句话摘要 |

### 5.2 目的

- 任何一个Agent换了，新来的能快速上手
- 同样的坑不踩第二次
- 团队成员之间有共同语言

## 六、交付规范

### 6.1 陈总只看结果

```
你只需要：
  ✅ 查看我输出的方案文档
  ✅ 做产品决策（选A还是选B）
  ✅ 验收最终成果

你不需要：
  ❌ 过问任何技术细节
  ❌ 参与代码审查
  ❌ 管团队内部事务
```

### 6.2 周报制度

每周一由我出一份简短的进度报告：

```markdown
# 周报：Week X（日期）

## 本周完成
- [功能A] 已完成开发方案 → 子Agent编码中
- [功能B] 已完成 → 待审查

## 下周计划
- [功能C] 启动开发方案编写
- [功能D] 代码审查

## 风险/问题
- ⚠️ XXX 需要陈总决策
- 供应商报价未回复

## 需要陈总确认
- □ [功能A] 是否按方案走？
```

## 七、附录：团队启动清单

```
□ 第1步：招募子Agent（硬件/小程序/后端各1名）
□ 第2步：搭建共享记忆库（决策/踩坑/术语）
□ 第3步：第一个任务 → 开发方案模板启动
□ 第4步：写"开发方案第1号——微信小程序框架搭建"
□ 第5步：分派给子Agent开发
□ 第6步：代码审查+验证
□ 第7步：合并入库
```
